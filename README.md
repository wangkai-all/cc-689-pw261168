# 巡检方案分析页

一个从零实现的小规模精确搜索前端：在候选巡检站点、每站费用、每站可覆盖设备清单之上，
找出费用、去重覆盖量与高风险设备覆盖量三项互不占优的完整方案前沿。

虚构样本包含 15 个候选站点、30 台设备（5 个设备组），刻意制造了强共享覆盖、一台只被
ST-E 覆盖的必检设备 P6，以及一台没有任何候选站点的 F6，用于展示结构性不可行诊断。

## 运行

```bash
npm install
npm run dev        # 开发服务器
npm test           # 单元测试 + 页面交互测试（vitest + jsdom）
npm run build      # 类型检查 + 生产构建
npm run preview    # 预览构建产物（127.0.0.1:4173）
```

截图脚本需要本地 Playwright 浏览器；在受限容器里本项目使用 `@sparticuz/chromium`
并以数据 URI 注入中文字体，见 `scripts/`。

## 计算口径

1. **先建覆盖集合**：每个站点映射为一个 30 位设备位图；方案覆盖是所有选中站点位图的按位并集，
   同一台设备只计一次。明细中的“各站覆盖数之和 − 重复覆盖 = 去重覆盖”与汇总指标来自同一份
   位图和同一次搜索结果。
2. **再穷举组合**：候选站点不超过 20 个时，对 2^N 个组合做精确 DFS；锁定站点先并入初始并集
   与费用，只穷举其余站点。每个叶子检查必检设备与各组最低覆盖量。
3. **三维非支配筛选**：费用不更高、覆盖不更少、高风险覆盖不更少，且至少一项严格更优，
   才判定支配。用 Fenwick 后缀最大值树在 O(n log n) 内筛掉被支配的指标组合，没有权重打分，
   也没有把各站覆盖数相加。
4. **预算只是筛选**：预算是已算好前沿上的过滤条件，不触发重新搜索；拖动预算只会让方案在
   “预算内 / 已退出”之间移动，并给出最低可行费用的差额。
5. **不可行诊断**：区分“必检设备没有任何候选站点”“组最低覆盖量超过可覆盖设备数”与
   “最低可行费用超过预算”三类，并分别指出具体设备、设备组与差额。

## 交互

- 点选图中任一点或表格行：查看选中站点、逐站新增/重复覆盖、漏掉设备与必检覆盖情况。
- 拖动预算线或下方滑块：看到哪些前沿方案退出可行范围；预算过低时给出差额提示。
- 锁定任一站点：以该站为固定前提重新搜索剩余站点，汇总显示锁定费用与搜索规模。
- 被支配样本：每个样本给出具体支配者与逐项差距（费用低多少、覆盖多几台等）。

## 源码结构

- `src/lib/coverage.ts` — 覆盖集合、位图与 20 站 / 30 设备上限。
- `src/lib/search.ts` — 精确 DFS、三维非支配筛选、方案明细与支配理由。
- `src/data/inspection.ts` — 虚构样本数据。
- `src/components/` — 约束面板、前沿图、方案明细、支配理由、不可行诊断、数据表。
- `src/lib/search.test.ts` — 用独立的 2^15 暴力枚举交叉验证前沿与可行数。
- `src/App.test.tsx` — 页面交互与“明细/汇总同源”的 DOM 测试。
